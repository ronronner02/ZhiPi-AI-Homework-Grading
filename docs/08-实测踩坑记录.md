# 08 · 实测踩坑记录

接入真实大模型、构造边界数据集压测链路的过程中，实际踩到并修掉的问题。
每条都有具体触发条件与实测数字，不是「最佳实践」清单。

写这份文档的原因：这些坑有一个共同特征——**出问题时界面看起来完全正常**。
分数、置信度、红黄绿分流全都有值，动线走得通，不报错。如果不知道去查哪一个
字段，可以一路把规则引擎的成绩当成大模型的成绩写进答辩材料。

## 一、最危险的失败模式：静默降级

`grade()` 的设计是「LLM 失败就降级 mock，保证演示不中断」。这个取舍对现场
演示是对的，但对**评测**是灾难——降级后界面照常出分，只有 `mode` 字段变了。

实际撞到三种降级路径：

| 触发条件 | 现象 | 判据 |
| --- | --- | --- |
| `ZHIPI_LLM_MODEL` 填了 embedding 模型 | 批改照常出分 | `mode: "mock"` |
| 网关响应超过硬编码的 30 秒 | 批改照常出分 | `mode: "mock"` |
| 本地直启没加载 `.env` | 上传提示「只能识别内置样例」 | `vlm_configured: false` |

第一种最隐蔽。`qwen3-embedding-8b` 只能输出向量、不支持 `/chat/completions`，
调用必然失败 → 静默降级。但 mock 规则引擎在内置样例上表现很好（11 份作答
预置了步骤标注），所以分数看着完全合理。

**唯一可靠的判据**，任何数字进报告之前先跑一次：

```bash
curl -s http://127.0.0.1:8010/api/demo/config
# 必须看到 "mode":"llm" 且 "vlm_configured":true
# 若是 "mode":"mock"，此刻测的是规则引擎，不是大模型
```

## 二、超时不能硬编码

`grader.py` 原本写死 `timeout=30`。这个值是按「课堂演示不能久等」定的，合理。
但实测同一网关、同一模型、同一 prompt 的耗时波动极大：

| 次数 | 模型 | 耗时 |
| --- | --- | --- |
| 1 | `deepseek-v4-pro-free` | 21.5s |
| 2 | 同上，同 prompt | 超时（>30s） |
| 3 | `DeepSeek-V4-Flash` | 60.6s |

30 秒在评测场景下会把「网关慢」记成「批改失败」，而失败会降级 mock——
于是报告里的准确率变成了规则引擎的成绩。

改成 `ZHIPI_LLM_TIMEOUT`，默认仍是 30（演示不变），范围 clamp 到 5–600。
**跑评测时必须显式调大**：

```bash
ZHIPI_LLM_TIMEOUT=240 py -3 tools/eval_harness.py <评测集>
```

## 三、指标可能在量错的东西

VLM 转写输出 `x^2-5x+6=0` / `x1=2, x2=3`，人工校对转写写的是
`x²-5x+6=0` / `x₁=2, x₂=3`。**数学含义完全相同**，逐字符比得出 20% CER。

三张图实测：

| 口径 | 平均 CER |
| --- | --- |
| 去空白（预注册口径） | 16.67% |
| 严格 | 17.52% |
| **记号归一（新增）** | **2.15%** |

不做归一化，「转写字准率」这个核心指标实际量的是「标注者的记号习惯是否
恰好撞上模型的记号习惯」，而不是「模型认没认对手写」。8 倍的差距会把结论
引向完全错误的方向。

处理方式：**新增第三个口径 `cer_math`，不动原有两个**。docs/07 是预注册方案，
口径先于数据确定，事后改动会失去可信度。三者并列写进报告，差距本身有信息量——
差得越大说明标注规范与模型输出习惯越不一致，该优先统一标注规范。

归一化只收敛「同义不同形」：上下标、全角符号、`解:` 类引导词。**刻意不做**
大小写折叠（英语作文里 `i` / `I` 是真实书写错误），也不删数字与运算符。
验证：`(x-2)(x+3)=0` vs `(x-2)(x-3)=0` 仍记错（加号误认成减号是真错误）。

## 四、校验顺序有安全含义

`validate_image` 的顺序是刻意的：**读文件头 → 格式白名单 → 像素上限 → 结构完整性**。

反过来会出事。构造了一个 167 字节的 PNG，文件头声明 30000×30000：

```
decompression_bomb.png    167 字节    RGB 30000x30000 = 900.0M px
```

如果先做解码类校验，解码器会先去分配 9 亿像素——**校验本身就成了拒绝服务的
入口**。像素上限必须早于任何解码动作。

另一个真实缺陷：截断文件被放行。`Image.open()` 只解析文件头，上传中断产生的
半个 PNG 能过校验，然后一路走到多模态接口才失败，白烧一次额度，还把底层报错
甩给体验者。补一道 `verify()`（只查 CRC 与结构、不解码像素）后拦下。

分类原则——**真实拍照会产出的必须放行**，否则是误伤用户：

| 必须放行 | 理由 |
| --- | --- |
| RGBA / 灰度 / 调色板 | 手机截图、扫描件常见 |
| EXIF 旋转 | 手机竖拍必然带 |
| 纯白 / 纯黑页 | 合法输入，交给识别层反馈「无内容」 |
| 1×1、1×4000 | 尺寸合法，内容无意义交给识别层判断 |
| `.png` 里装真 JPEG | 内容在白名单内，扩展名不该成为拒收理由 |

| 必须拒收 | 理由 |
| --- | --- |
| 空文件 / 全零字节 / 文本伪装 | 不是图片 |
| 截断文件 | 走到接口才失败，白烧额度 |
| 超像素上限、解压炸弹 | 内存风险 |
| GIF | 白名单外 |

## 五、分母的选择就是诚实度

分流安全性的四象限：

| 象限 | 含义 | 严重程度 |
| --- | --- | --- |
| hit | 该看的拦住了（判黄/红） | — |
| **miss** | **漏拦：该看的被自动通过** | **最严重** |
| false_alarm | 误拦：不必看的被转人工 | 浪费教师时间 |
| pass_ok | 不必看的自动通过 | 理想 |

漏拦率的分母**刻意用「教师认为该看的份数」，不用全体样本**。用全体做分母会
把数字稀释得很好看，是自欺欺人。举例：6 份样本、其中 3 份人工认为必须过目、
漏了 1 份 —— 正确算法是 1/3 = 33%，用全体算是 1/6 = 17%。

这一项不能被「分桶校准」替代。分桶校准回答「AI 说绿的时候准不准」，
漏拦率回答「教师认为必须看的，AI 放过了多少」。一个系统可以每桶都很准，
却恰好把少数高风险作答判进了绿桶。误拦只浪费教师时间，漏拦会把错误批改
直接发到学生手上，两者严重程度不对等，必须单列。

## 六、一条错标能毁掉整份报告

标注是人手工填的，错填是常态而非例外。实测三个后果：

| 错标 | 后果 |
| --- | --- |
| `human_score: 9999` | MAE 变成 **9991**，报告照样生成，看不出异常 |
| `human_score: null` | 整轮评测 **TypeError 崩在中途** |
| `needs_review: "false"` | `bool("false")` 为 `True` → 「不必复核」被算成「漏拦」，安全性指标**反着走且毫无征兆** |

第三条最阴。非空字符串转布尔恒为真，所以一个手误写成字符串的 `"false"`
会让指标反向，而输出看起来完全正常。

处理方式：把校验放在 `load_manifest`，**跑之前就拦下**，不在跑的过程中救。
逐条报错并说明理由，宁可啰嗦也不让脏数据无声污染答辩材料。

分级处理，不是一律拒收：

- **拒收**：类型错、分数越界、`needs_review` 非布尔、题目 ID 不存在
- **放行 + 警告**：枚举外错因标签（枚举本身会演进，但要提醒它永远不会与
  AI 标签相交、会把 Jaccard 拉低成 0 却看不出原因）
- **放行 + 自动修正**：重复错因标签（去重即可，不该打断评测）
- **放行**：`null` 视为「这条没标」，与字段缺失同义；小数分（教师给 7.5 分很常见）

## 七、VLM 自评清晰度不可轻信，且它单独救不回分流

用 `14_worst_case.jpg`（歪 8° + 暗 0.58 + 模糊 1.6px + 噪点，叠加劣化）实测：

| 项 | 值 |
| --- | --- |
| VLM 自评 clarity | **90.0** |
| 实际转写错误 | 1 处（`x=2` 漏了负号，真值 `x=-2`） |
| CER（记号归一） | 3.2% |

转写质量其实不错（3.2%），但**自评清晰度 90 明显虚高**——这张图人眼看都费劲。
`ocr_clarity` 是 §9.7 五因子里权重 0.25 的一项，虚高会直接抬高总置信度。

更值得注意的是另一半：把 clarity 如实压低也救不回分流。固定其余四因子在
「模型自信且答案成形」的典型值（answer_match 90 / rubric_coverage 100 /
llm_self_consistency 92 / teacher_pass_rate 88），只动 clarity：

| clarity | 置信度 | 分流 |
| --- | --- | --- |
| 90（VLM 自评） | 92.2 | 绿·自动通过 |
| 70 | 87.2 | 绿·自动通过 |
| 60 | 84.7 | 黄·教师确认 |
| 45（如实值） | 81.0 | 黄·教师确认 |
| 30 | 77.2 | 黄·教师确认 |

clarity 从 90 掉到 45（−45 分）只把总置信度拉低 11.2 分，**跨过绿线进黄桶，
但到不了红桶**。换句话说：红桶实际由 `answer_match` + `rubric_coverage` +
`llm_self_consistency`（合计权重 0.65）决定，转写清晰度单独说不上话。

这对「多模态批改的主要失败发生在转写」这个主张有直接影响——如果转写坏了但
答案恰好成形，现有权重不会把它送去人工。两条可查的方向：

1. 校准 VLM 自评（或改用可测的图像质量指标替代自评），别让模型给自己打分；
2. 考虑给 clarity 加**硬闸**：低于某阈值直接强制转红，而不是只参与加权平均。

暂未改动权重——§9.7 的口径是预注册的，改之前需要真实数据支撑，
而不是拿合成图的观测去调。

## 七补 · 满分卷 Rubric 覆盖度被打成 0

**现象（真实上传截图）**：物理速度题 AI 判 **6/6**，四步全部 ✓ 且每步有
`evidence`（`v=s/t`、`200/20`、`10`、`m/s`），但五因子里 **Rubric 覆盖度 = 0**，
总置信度被压到 **76.8 黄桶**。题目判对了，分流却说「评分点没覆盖全」。

**根因有两层**：

1. **Prompt 旧口径**把 `reason` 写成「错误位置与原因」——模型在全对步骤上
   合理省略 reason，只留 evidence；
2. **`derive_factors` 旧实现**只统计 `reason` 非空：
   `covered = sum(1 for s in step_analysis if s.get("reason"))`。
   于是「有证据、无错因说明」的满分步全部算未覆盖 → 覆盖度 0。

这不是老师看错，是因子定义把「可解释完整性」窄化成了「写出错因」。

**修复（已落地）**：

| 点 | 改动 |
| --- | ---- |
| 覆盖判定 | `reason` **或** `evidence` 任一非空即算该步已覆盖（`_step_has_judgment`） |
| 解析回填 | 有 evidence 无 reason 时，补「该步正确/部分正确/未得分，依据作答原文判定」 |
| Prompt | 明确正确步骤也必须写 reason；JSON 示例改为「判定理由（正确/错误均须填写）」 |
| 回归 | `demo/tools/test_rubric_coverage.py` 用截图同款四步 evidence-only 样例锁 100 分覆盖度 |

对截图同款因子重算（其余不变：clarity 95 / match 100 / self 100 / pass 80）：

```text
旧：coverage 0   → 置信度 76.8 黄
新：coverage 100 → 置信度 96.8 绿
```

**未改**：§9.7 权重与 85/60 阈值；mock 预置因子路径。

## 八、中转网关会随机吐 400，且必须重试

跑完 14 张走查图才暴露：**同一张图连打 10 次全成功，走完整链路 14 张里挂 3 张**。
错误正文是 `400 {"error":{"message":"API key not valid","type":"upstream_error"}}`。

按 HTTP 语义 4xx 不该重试——但这里必须重试。原因：中转网关在多个上游 key 之间
轮询，轮到失效的那个就把上游的 400 原样透出来。它取决于**轮到哪个上游**，
与我们发了什么无关。

两个坑叠在一起，先前完全查不动：

1. `resp.raise_for_status()` 只抛「400 Bad Request」，不带网关正文。
   改成手动带出正文后 `API key not valid` 才浮现——在此之前连方向都判断不了；
2. 识别（`ocr.py`）与批改（`grader.py`）**两条路径都没有重试**。

修法：两处各加瞬时故障重试，3 次尝试、1.2s/2.4s 退避。判据刻意收窄：

| 重试 | 不重试 |
| --- | --- |
| `api key not valid`（轮到失效上游） | `404 model_not_found`（模型名写错） |
| `no available channel` | `401 Incorrect API key`（本地 key 配错） |
| `upstream` / `rate limit` / 429 / 5xx | `400 messages too long`（请求本身有问题） |

同一批 14 张：**3 张失败 → 0 张失败**。

不重试的后果不是「少一条数据」，而是体验者上传一张正常照片、随机看到
「识别失败」，会以为是自己照片的问题——而这恰恰是我们最想证明能处理好的环节。

## 九、answer_match 因记号差异掉到 25.8

识别按 Prompt 输出线性写法 `x^2-5x+6=0 / x1=2, x2=3`，题库标准答案是人写的
`x² - 5x + 6 = 0 → x₁ = 2，x₂ = 3`。抽数值时 ASCII 的 `x1` 被读成「数字 1」，
凭空多出标准答案里没有的数，`s_nums ⊆ a_nums` 判定失败。

后果：一份**完全正确**的作答，answer_match 从 100 掉到 **25.8**，
总置信度 96.8 → 78.2，分流从绿变黄。绿桶（自动通过）因此几乎永不触发——
而「高置信自动通过、低置信转人工」正是这套系统的核心卖点。

修法：`_norm_notation()` 在抽数值前把 ASCII 收敛到 Unicode 上下标
（`x^2`→`x²`、`x1`→`x₁`），只处理同义不同形，不碰独立数字、运算符与单位。

| 输入 | 修复前 | 修复后 |
| --- | --- | --- |
| VLM 线性写法（正确作答） | 25.8 | **100.0** |
| Unicode 写法（内置样例） | 100.0 | 100.0 |
| `x1=2, x2=4`（数值真错） | — | 22.6 |
| `x1=2`（只写一个根） | — | 14.3 |

关键是后两行：归一化没有变成粉饰工具，真错误仍然被扣。

这与 §三 的 CER 记号归一是**同一类问题的两个位置**：一个影响评测指标，
一个影响线上分流。根因都是「人写标准答案用印刷体记号，模型输出用线性记号」。

## 十、可选增强不该拖累核心链路

`_maybe_cross_check`（双模型交叉验证）用第二模型复核黄/红结果。实测
grok-4.5 **静默挂 30 秒才失败**，把一次 5 秒的批改拖成 35 秒。

它是增强项：拿不到结论只少一份佐证，主批改照样可用。让可选环节按主流程的
超时等待，等于把它的不确定性转嫁给核心链路。拆成独立超时
`ZHIPI_CROSS_TIMEOUT`（默认 12 秒，主批改仍 30）。

实现上有个坑：最初想用「临时改 `os.environ` 再还原」传超时，这在 uvicorn 下
是错的——同步端点跑在线程池里，并发请求会互相覆盖环境变量。改成按参数传。

## 十一、演示要的是快模型，不是大模型

批改模型换过四轮：

| 模型 | 耗时 | 结果 |
| --- | --- | --- |
| `qwen3-embedding-8b` | — | 不支持 chat，静默降级 mock |
| `deepseek-v4-pro-free` | 21.5s / 超时 | 波动极大 |
| `DeepSeek-V4-Flash` | 60.6s / 90s 超时 | 不可用 |
| `glm-5.1` | 57.1s | 9/10 正确 |
| **`gemini-3.1-flash-lite-preview`** | **2.3s** | **10/10，证据链完整** |

最终配置：批改**复用 VLM 凭据**（`grader.llm_credentials()` 本就有这条回退路径），
一个网关一个模型，出问题的地方最少。

`glm-5.1` 57 秒能出正确结果，但演示时每次上传要转圈一分钟。**慢模型配大超时
只是把「失败」换成「等待」**，体验一样差。演示需要 5 秒级。

## 十二、零分卷被自动通过：置信度不等于正确性

走查 `06_blur_light.jpg` 时出现：**AI 判 0/6，置信度 86.8，分流绿·自动通过**。

AI 的判断完全正确——学生把速度公式写反成 `v=t/s`，四步全错，错因标注为
「公式选择错误 / 计算错误 / 单位错误」，教师提示写得也准。问题不在判分，
在分流：一份 0 分的作业**没有经过任何教师复核就被放行了**。

根因是五因子的语义构成。只有 `answer_match` 反映「学生答得对不对」，
其余四项反映「AI 对自己的判断有多确定」：

| 因子 | 权重 | 度量的是 | 学生全错时 |
| --- | --- | --- | --- |
| ocr_clarity | 0.25 | 卷面清晰度 | 95（卷面本身没问题） |
| answer_match | 0.25 | 学生终答 vs 标准答案 | 60（封顶值） |
| rubric_coverage | 0.20 | 逐步判定完整性 | 100（每步都判了） |
| llm_self_consistency | 0.20 | 模型自我一致 | 100（很确定） |
| teacher_pass_rate | 0.10 | 历史通过率 | 80 |

于是「AI 非常确定这份全错」被加权成高置信度，读作「不必人工复核」。
实测该组合下的分流：

| 场景 | 置信度 | 分流 |
| --- | --- | --- |
| 全错但 AI 很确定（实测） | 86.8 | **绿·自动通过** |
| 全错 + 数值完全不搭（match 30） | 79.2 | 黄 |
| 全错 + 卷面也差（clarity 50） | 75.5 | 黄 |
| 全对（对照） | 96.8 | 绿 |

mock 模式下没暴露，因为内置样例的因子是预置的、数值偏保守。**只有接真实模型
才会出现「模型对自己很自信」这种输入组合**。

**未改动**，因为这属于 §9.7 的口径决策，不是 bug 修复：

- 一个方向是加硬闸：得分率 0（或低于某阈值）时无论置信度多高都不自动通过。
  理由是运营性的而非技术性的——一份 0 分直接发到学生手上，是家长最容易质疑、
  老师最不能接受的场景，「AI 判得准」不构成跳过老师的理由。
- 另一个方向是重新审视因子语义：把「对判断的确定性」与「作答的正确性」分成
  两个独立维度，而不是加权成一个数。

两条都需要真实数据支撑再定，且要同步改 docs/07 的预注册口径。**列入待决清单**。

## 十三、网关稳定性决定批量评测的可行性

§八 讲的是随机 400（可重试）。这里是另一件事：**速率**。

免费 / 中转通道对单次演示够用，对批量评测不够。实测 3 条数据：

- 总耗时 611 秒
- `SUB003` 三次重试全部超时（每次 150 秒）
- `grok-4.5` 首测通、复测 `503 No available channel`

按这个速率，30 张照片约两小时且必然有失败。评测报告里会点出哪些条目靠重试
才成功——一份靠反复重试凑齐的数据，可信度应该打折。

跑批量评测前把超时显式调大（`ZHIPI_LLM_TIMEOUT=240`），否则「网关慢」会被
记成「批改失败」，而失败会降级 mock，报告里的准确率就变成了规则引擎的成绩。

## 十三之二、静默降级让「配了」和「生效」变成两件事

第二模型交叉验证与二次批改一致性都**按设计静默失败**：拿不到结论就跳过，
主批改照常出结果。这个设计是对的（可选增强不该拖垮核心链路），但副作用是
配置错误在界面上完全不可见。

实际状态曾是：`ZHIPI_LLM_API_KEY_2` / `BASE_URL_2` / `MODEL_2` 三件套齐全、
模型也真能调通，但 `ZHIPI_CROSS_TIMEOUT=12` 而第二模型单次要 45–91 秒，
于是**每一次黄 / 红批改都白等满 12 秒、拿到 `None`、被 `except` 吞掉**。
比不启用更差：付了等待成本，没换来任何佐证。同期 `ZHIPI_DOUBLE_CHECK=0`
把二次复批也关了，`llm_self_consistency`（权重 0.20）静默退回模型自报值。

各候选实测耗时（中转网关，同一道题重复批）：

| 模型 | 耗时 | 判分表现 |
|---|---|---|
| `grok-4.5` | 77–91s | 同一错卷给 4 / 2 / 3 分，转红判定在多次运行间翻转 |
| `glm-5.2` | 45–65s | 错卷 4 / 5 / 5，与主模型差 0–1 分 |
| `glm-4.5-flash` | 49–72s | 满分卷扣到 9 分；错卷 2–4 分漂动，跨越转红阈值 |
| `minimax-m3` | 25–90s（中位 62） | 错卷三次均 4 分、满分卷两次均 10 分，差稳定 1.0 分 |

三条结论：

1. **名字带 flash / fast 的不一定快。** 上表四个候选没有一个能装进 12 秒，
   而主模型 `gemini-3.1-flash-lite-preview` 只要 3.4 秒。
2. **裁判自己不稳，比没有裁判更糟。** 转红阈值是满分 15%（10 分题即 1.5 分），
   `grok-4.5` 的判分离散度就横跨这个阈值——同一份作业两次演示会得到不同分流，
   这是答辩上最难解释的一类现象。`glm-4.5-flash` 给满分卷扣分同理：
   它会把好卷误判成「两模型分歧」强制转人工，用噪声灌满人工队列。
3. **超时预算必须由实测决定，不能凭默认值。** 现配 `minimax-m3` + 120 秒，
   实测黄件 47–60 秒拿到结论。代价是黄 / 红件单份等待约 70 秒
   （3.4 主批改 + 3.4 二次复批 + ~62 交叉验证），绿区不受影响。

顺带修掉一个真实缺陷：`_call_llm` 的重试循环原先只覆盖「拿到了 HTTP 错误响应」，
`requests.post` 裸在循环里，连接层异常（SSLError / ConnectionError）直接穿出去
不重试。而这个网关在连发长请求后会瞬时拒连，恰好落在这个盲区里——
外层又是 `except: return None`，于是记成「第二模型没结论」。现已纳入重试。

配置项自查：`.env.example` 里原先只在注释中**提到** `ZHIPI_CROSS_TIMEOUT`，
却没有这一行配置。照模板部署的人拿到的是 12 秒缺省值，必然踩同一个坑。已补。

## 十四、流程教训

**动手前先搜一遍现有工具。** 我写完 `eval_metrics.py` 才发现仓库里已有
`eval_harness.py`（35KB，指标口径对齐 docs/07 §3 的预注册方案），
而且是我那份的严格超集。白做一轮还得删掉。

两套指标实现并存是真实风险：有人跑错脚本，答辩材料里就出现两个不一致的数字。
最后的处理是删掉自己写的，把新增能力（漏拦率、记号归一）并进既有 harness。

**自测过的数据不构成独立证据。** 我测过的数据必然带着「我知道它会怎么失败」
的偏见，修完一定通过。所以边界数据集分了 `tested/` 与 `holdout/`——
后者用不同随机种子生成，我不查看、不跑断言，留给人工独立验证。

**压测别把网关打崩了再去怪模型。** 排查第二模型时我连发了十几个 60–90 秒的
请求，之后网关开始拒连（`SSL UNEXPECTED_EOF_WHILE_READING`，0.3 秒就失败）。
我据此写下「glm-4.5-flash 失败率 36%」——是错的。把调用间隔拉开、并单独验证
`GET /models` 仍返回 200 之后，同一个模型 3/3 成功。**判定"是模型的问题"之前，
先证明网关此刻是好的**：留一个不经过模型的探针（`/models`）和一个已知快的
对照模型（主模型 3 秒返回），两者都正常才能把锅算到候选模型头上。
