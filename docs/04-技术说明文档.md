## 2. OCR 与手写识别方案

作业图像质量参差、手写体多样、公式与图形并存，是批改准确率的第一道瓶颈。本章对应设计方案 §9.1、§9.2、§11.4，代码实现为 `demo/pipeline/ocr.py`。

### 2.1 双引擎总体设计【Demo 已实现】

为保证"输入作业图片 → 输出批改结果"链路**在任何环境（含无网络、无凭据的比赛现场）都能完整演示**，识别层采用双引擎架构：

| 引擎 | 触发条件 | 能力 | 定位 |
| ---- | -------- | ---- | ---- |
| **vlm（真实多模态识别）** | 配置 `ZHIPI_VLM_API_KEY` | 识别**任意**手写作业照片，转写文字 / 公式 / 英文并自评卷面清晰度 | 真实识别路径，现场联网演示与生产原型 |
| **sample-match（离线演示识别）** | 未配置密钥（默认） | 感知哈希匹配内置 11 张样例作业照片，命中后返回该样例的标准转写 | 演示兜底路径，完整模拟"拍照 → 识别"体验 |

两种引擎返回统一结构 `{"engine", "text", "clarity", "matched_submission_id"?}`，识别失败返回 `{"engine": "none", "error": 引导提示}`。统一入口 `recognize_image()` 的优先级与降级顺序：

1. 已配置 VLM 密钥 → 真实多模态识别；调用失败但图片命中内置样例 → 自动降级 sample-match；
2. 未配置密钥 → 感知哈希匹配内置样例；
3. 均不可用 → `engine="none"`，返回"配置 ZHIPI_VLM_API_KEY 后可识别任意照片"的引导提示，不误报结果。

**诚实说明**：离线演示模式是为脱网演示设计的工程兜底，它验证的是"图片进、批改出"的**链路完整性**，不代表真实手写识别精度；真实识别精度取决于所接多模态模型，其字符错误率（CER）等指标按评测方案（docs/07 §3.1、表 A）在真实手写样本上实测，**当前为待实测状态**。

### 2.2 真实模式：多模态大模型转写【Demo 已实现】

配置 `ZHIPI_VLM_API_KEY` 后，作业照片以 data URI 形式发给 OpenAI 兼容的多模态接口（`{base_url}/chat/completions`）：

| 环境变量 | 缺省值 | 说明 |
| -------- | ------ | ---- |
| `ZHIPI_VLM_API_KEY` | 无（必填） | 多模态接口密钥 |
| `ZHIPI_VLM_BASE_URL` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 默认阿里云百炼 compatible-mode，可换任意 OpenAI 兼容服务 |
| `ZHIPI_VLM_MODEL` | `qwen-vl-max` | 默认通义千问多模态旗舰，符合"国产模型优先"（设计方案 §13.1） |

转写 Prompt 全文（`ocr.py` 中 `VLM_PROMPT`，体现"只转写、不批改"的职责分离与防幻觉约束）：

```text
你是一个手写作业识别引擎。请把图片中「学生手写的作答内容」逐字转写出来：
1. 只转写手写部分，忽略印刷体题目、姓名、班级抬头；
2. 数学公式用线性写法（如 x^2-5x+6=0、v=s/t），保留换行；
3. 若字迹无法辨认，用〔?〕占位；
4. 最后评估卷面清晰度 clarity（0-100：90+ 工整清晰，60-89 可辨认，60 以下潦草模糊）。
只输出 JSON：{"text": "转写文本", "clarity": 数字}
```

工程要点：

- **temperature=0**、超时 90 秒；返回内容经容错 JSON 解析（容忍模型以 Markdown 代码块围栏包裹 JSON）；
- `clarity` 强制 clamp 到 [0, 100]，解析失败回退 75，**该值直接作为置信度公式的 ocr_clarity 因子**（本文 §6.2）；
- 无法辨认字符以 `〔?〕` 占位进入转写文本，批改 Prompt 据此触发 `legible=false` 与降置信度（本文 §5.2）；
- 前端在 vlm 模式下将转写文本置为**可编辑**：教师可先修正识别结果再发起批改，"教师可控"贯穿识别环节（设计方案 §11.3）。

生产环境的完整转写校对 Prompt（LaTeX 输出、逐行置信度、涂改说明、不确定候选列表）见 `prompts/grading_prompts.md` Prompt 5，为 Demo 版的超集【设计完成·入围后实施】。

### 2.3 离线演示模式：SHA-256 + 2048 位增强 dHash【Demo 已实现】

未配置密钥时，上传图片与内置样例图库做两级比对：先 SHA-256 精确匹配（原图直传场景零成本命中），未命中再计算**增强差值感知哈希（dHash）**比对。针对"同版式作业纸、低对比度、同题不同作答"的场景，对经典 64 位 dHash 做了三点强化（`ocr.py` 中 `dhash()`）：

1. **自动对比度拉伸**（`ImageOps.autocontrast`）：避免均匀纸面导致哈希坍缩；
2. **水平 + 垂直双向梯度**：捕捉笔画结构，而非只看行方向亮度变化；
3. **32×32 网格共 2048 位**（水平 1024 + 垂直 1024）：足以区分同一道题不同学生作答的细微差异。

匹配判定为**阈值 + 次优间隔**双条件：最优命中的汉明距离 ≤ 50，且与次优命中的距离差 ≥ 8（防止近似样例间误配）；任一不满足则判为不匹配，宁可提示"仅支持内置样例"，不做没有把握的猜测——与批改层"AI 没把握主动交人工"（设计方案 §6.5）同一原则。

阈值取值依内置样例集**开发期实测标定**（标定记录见 `ocr.py` 注释）：

| 标定项 | 实测汉明距离 | 结论 |
| ------ | ------------ | ---- |
| 同一样例的重编码 / 缩放变体 → 本体 | ≤ 42 | 阈值 50 可稳定召回常见传输变形 |
| 不同样例两两之间（最小值） | 65 | 与阈值 50 有明确间隔，不会互相误配（本次文档更新时按现行 11 张样例复核，最小值仍为 65） |
| 无关图片 → 任意样例 | ≥ 285 | 远超阈值，不会把无关照片误认成样例 |

> 上述为开发期在内置样例集上的标定数据，用于说明阈值设定依据；不构成对任意真实照片检索精度的承诺。离线模式的定位始终是演示兜底（§2.1 诚实说明）。

### 2.4 内置手写样例图片的生成原理【Demo 已实现】

11 张样例作业照片由 `demo/tools/gen_sample_images.py` 从 `submissions.json` 的 11 份作答**确定性渲染**生成（`SUB001.png` – `SUB011.png` + `manifest.json`，清单含每张图的 SHA-256），核心机制：

1. **页面版式**：作业纸抬头（班级 / 学科印刷体 + 学生姓名手写）→ 印刷体题干（宋体，含分值）→ 横线作答区 → 手写作答；
2. **手写模拟**：楷体（中文 / 数学）与 Segoe Print（英文）**逐字符渲染**——每个字符独立抖动基线（±1.8px）、水平位置（±1.2px）、字号（±4%）与墨色深浅，潦草卷面下个别字符再叠加 ±6° 倾斜；上下标字符（²、₁ 等）按缩放 + 垂直偏移单独排版；
3. **清晰度分档做旧**：以作答预置的 `ocr.clarity` 推出潦草度 `messy = clamp((92 − clarity) / 45, 0, 1)`——清晰度越低，抖动越大、墨色越浅（灰墨）、叠加涂改划线（messy > 0.5 时 1–2 处）与更重的高斯模糊，模拟真实低质量卷面；
4. **拍照效果**：整页 ±1.4° 随机旋转置于深色桌面，叠加纸张阴影、约 0.4% 像素噪点与暗角，模拟手机随手拍；
5. **确定性种子**：全部随机量以 `submission_id` 为种子（噪点用 `submission_id + "_noise"`），**重复运行输出逐字节一致**，保证 manifest 中 SHA-256 与感知哈希索引长期有效。

这套生成器使离线演示的"拍照上传"环节具备真实感（不同清晰度对应不同分流结果），同时全部内容与 `submissions.json` 的预置转写严格一致，识别 → 批改链路可交叉核验。

### 2.5 生产化识别方案规划【设计完成·入围后实施】

生产环境将在多模态直转的基础上引入专用识别底座，方案与设计方案 §9.1、§9.2、§13.1 一致：

**图像预处理流水线**：去阴影与光照均衡（背景估计 + 除法归一化）→ 自动裁边与透视矫正（最大四边形轮廓拟合）→ 自适应二值化（保留淡色铅笔字）→ CLAHE 对比度增强 → 版面分析（切分文本行 / 公式块 / 图形块）→ 题目—答案区域分割。全部可本地私有化运行，不外传原图（设计方案 §19.5）。

**识别引擎选型对比**：

| 引擎 | 适用对象 | 手写与公式能力 | 部署方式 | 许可 |
| ---- | -------- | -------------- | -------- | ---- |
| PaddleOCR | 印刷体 / 手写文字、版面分析 | 文字强；手写中文中等；公式需外接 | 本地私有化 | Apache-2.0 |
| Pix2Text | 数学公式转 LaTeX | 印刷公式强、手写公式中等 | 本地私有化 | MIT |
| Mathpix | 手写公式转 LaTeX | 业界领先 | 云 API（境外） | 商业 SaaS |
| Qwen-VL 系列 | 整图理解、手写、公式、图形语义 | 较强，具语义理解 | 云 API / 可私有化 | 商业，已备案 |
| GLM-4V | 整图理解、手写、公式、图表推理 | 较强 | 云 API / 可私有化 | 商业，已备案 |

**推荐组合**：PaddleOCR（版面 + 常规文字）+ Pix2Text（公式 LaTeX）构成可离线的低成本底座；Qwen-VL / GLM-4V 承担复杂版面、连笔手写、几何 / 电路 / 受力图语义与整体转写校对（Prompt 5）；境外服务（Mathpix、GPT-4o、Gemini）仅作离线评测对照，不进入生产数据链路，避免学生作业数据出境。

**手写难点对策**：连笔涂改 → 转写标注不确定而非猜测；公式二维结构 → LaTeX 保留结构后规范化比对；图形题 → 多模态输出结构化语义描述（节点 / 连接 / 方向）交 LLM 判断；中英混排单位符号 → 归一化词表（`grader._NUM_UNIT_RE` 的长单位优先正则即该词表的 Demo 版）。

### 2.6 识别质量信号与降级【Demo 已实现】

1. **质量信号入置信度**：识别引擎输出的 `clarity`（0–100）直接进入置信度公式（权重 0.25，本文 §6）；清晰度低的作答（如内置样例 SUB003 clarity=55、SUB009 clarity=58）加权后落入红色区间，系统不强行批改；
2. **不确定内容显性化**：转写中 `〔?〕` 占位与批改输出的 `legible=false` 步骤在前端以"⚠ 该步字迹难以辨认，建议教师人工复核"醒目提示（本文 §5.3）；
3. **教师修正转写**：vlm 模式下教师可修正转写文本后再批改（§2.2），修正行为在生产环境将沉淀为识别难例样本，用于后处理规则与微调语料【设计完成·入围后实施】；
4. **实测指标**：识别质量以 CER（字符错误率）按清晰度分桶实测，指标口径与结果见评测方案 §3.1 / 表 A（待实测）。

## 3. 知识建模方案

知识建模是错因诊断与薄弱分析的骨架。系统采用"知识点体系 + 两层标签 + 题目/Rubric 结构化 + 画像与学情聚合"，对应设计方案 §6.11、§9.3、§9.4、§6.14–§6.20。

### 3.1 学科知识点体系

系统为每个学科维护一棵三层知识树（学科 → 知识领域 → 知识点），知识点作为第一层标签的取值域。首期覆盖初中数学、初中物理与英语写作（设计方案 §4.2）。完整知识树为知识库设计【设计完成·入围后实施】，Demo 题库使用其中的子集（§3.3）。

│  ├─ 有理数运算
│  ├─ 整式与因式分解
│  ├─ 一元一次方程

├─ 函数
│  ├─ 一次函数

### 3.2 两层标签体系【Demo 已实现】

系统对每道题打两层标签（设计方案 §6.11）：**第一层为知识点标签**（取值来自知识树，Demo 中挂在 Rubric 每步的 `knowledge_point` 字段上），回答"错在哪个知识点"；**第二层为错因标签**，回答"为什么错"。错因标签枚举严格采用设计方案 §6.11 定义的十类，不增不减：

| 错因标签 | 定义 | 典型判定规则 |
| -------- | ---- | ------------ |
| 概念理解错误 | 对概念、定义、定理的理解本身有误 | 公式/方法选择错误且根源在概念混淆；非计算或书写层面偏差 |
| 公式选择错误 | 选用了不适用于本题情境的公式 | 标准解法要求公式 A，学生使用不适用的公式 B（如 Demo 样例 SUB006 将 v=s/t 写成 v=t/s） |
| 步骤缺失 | 解题链缺少必要关键步骤 | Rubric 某得分步骤在作答中完全无对应内容（如 SUB002 漏掉第二个根） |
| 计算错误 | 公式与步骤正确，数值运算出错 | 代入正确但运算结果与正确值不符（如 SUB003 因式分解常数项不符） |
| 单位错误 | 数值正确但单位缺失、写错或换算错误 | 最终数值正确而单位不符（如 SUB005 把 m/s 写成 km/s，复现设计方案 §6.3 示例） |
| 审题错误 | 未正确理解题意或遗漏条件 | 关键条件被忽略、答非所问（如 SUB009 英语作文跑题） |
| 图形理解错误 | 对几何图、电路图、受力图、函数图像的理解有误 | 电路结构识别错误、图像平移方向误判等 |
| 符号书写错误 | 符号书写不规范或笔误 | 正负号、上下标笔误、英文拼写错误（如 relaxd / intresting） |
| 表达不完整 | 结论或论述不完整 | 有过程无结论、要点表达残缺 |
| 答案正确但过程不规范 | 答案正确但过程跳步或不规范 | 结果正确但缺公式原式等必要书写（如 SUB010） |

**枚举的工程强约束**（三道闸门，均已实装）：

1. **Prompt 约束**：批改 Prompt 明确"错因标签必须从【可选错因标签】中选择，不得自造标签"（本文 §5.2）；
2. **解析过滤**：`grader.py` 对 LLM 返回与 mock 预标注中的错因标签逐一校验，不在 `ERROR_TAGS` 枚举内的直接丢弃置 `None`；
3. **终审校验**：教师改判错因时，`POST /api/teacher/review` 对每个标签校验枚举成员资格，含非法标签整单拒绝并返回 422（本文 §7.4）。

错因产生走"规则 + LLM"混合路径：mock 模式为数据侧按规则口径预标注；llm 模式由批改模型在枚举内逐步归因；规则难以覆盖的复杂主观题另备错因归因专用 Prompt 2（`prompts/grading_prompts.md`，最多 2 个标签 + ≤80 字判定依据）【设计完成·入围后实施】。

### 3.3 题目结构化与 Rubric 建模【Demo 已实现】

Demo 题库（`demo/data/questions.json`）实装的题目模型如下，兼容设计方案 §9.3 的字段口径并扩展：

```jsonc
{
  "question_id": "Q002",                    // 题目唯一 ID
  "subject": "物理",                        // 学科（数学 / 物理 / 英语）
  "grade": "初二",                          // 学段
  "question_type": "计算题",                // 题型（计算题 / 短文写作 …）
  "title": "速度与单位换算",                 // 题目短标题（工作台 / 台账展示用）
  "knowledge_points": ["速度公式", "单位换算"],  // 第一层知识点标签
  "question_text": "…求汽车行驶的速度 v。",   // 题干
  "standard_answer": "v = s / t = 200 m ÷ 20 s = 10 m/s",
  "standard_solution_steps": [              // 标准解题步骤（字符串数组），注入批改 Prompt
    "明确匀速直线运动求速度，先写出公式原式 v = s/t",
    "代入已知量：v = 200 m ÷ 20 s",
    "计算得数值结果 v = 10",
    "补全单位，写出最终结果 v = 10 m/s"
  ],
  "max_score": 6,                           // 本题满分
  "rubric": [                               // 评分规则：逐步分值 + 步骤级知识点
    {"step_id": 1, "step": "写出正确公式", "max_score": 2, "knowledge_point": "速度公式"},
    {"step_id": 2, "step": "正确代入数值", "max_score": 2, "knowledge_point": "速度公式"},
    {"step_id": 3, "step": "计算结果正确", "max_score": 1, "knowledge_point": "速度公式"},
    {"step_id": 4, "step": "单位正确",     "max_score": 1, "knowledge_point": "单位换算"}
  ]
}
```

设计要点：

1. **`standard_solution_steps` 是批改质量的关键输入**：以自然语言列出标准解法的每一步，与 Rubric 逐步对应，注入批改 Prompt 供步骤级比对（旧题目缺失该字段时容错为"未提供，请参考标准答案"）；
2. **`rubric[].knowledge_point` 把知识点标到步骤粒度**：学情聚合因此能以"Rubric 步骤"为最小统计单元计算知识点错误率（§3.4），而不是粗粒度的"整题对错"；
3. **三题覆盖三类批改能力**：Q001 数学计算题（步骤识别与计算错误定位）、Q002 物理计算题（公式判断与单位检查）、Q003 英语短文写作（表达分析与主观维度评分），对应设计方案 §11.2；
4. **自动判题**：任意上传图片识别后，按转写文本与各题"题面 + 标准答案"的 difflib 相似度自动判定所属题目，命中知识点关键词加权 +0.1，英文作答对英语题加权 +0.15（`app.py` `_detect_question`）。

生产环境的完整 JSON Schema（含 `criteria` 判分要点、`linked_error_tags` 步骤失分 → 错因候选先验映射、`difficulty` 等扩展字段）以本节实装模型为基础向上扩展【设计完成·入围后实施】。

### 3.4 学生画像与班级学情建模【Demo 已实现】

**作答数据模型**（`submissions.json`，11 份作答 / 9 名学生）：每份作答含 OCR 预置转写与清晰度、五个置信度因子预置值（mock 模式演示用，见 §6.2），以及**逐步预标注** `step_annotations`——每步的 `is_correct` / `partial_ratio`（部分分比例）/ `error_tag` / `reason` / `evidence`（学生原文证据片段）/ `legible`（可辨认标记），构成 mock 模式下确定性的证据链批改数据源。

**学生长期画像**（`analytics.aggregate_student`，端点 `/api/analytics/student/{id}`）：

1. **跨题聚合**：按学生姓名聚合本次全部作答（如张明一人 3 份：数学 / 物理 / 英语），以 Rubric 步骤为最小统计单元产出错因频次、薄弱知识点（仅保留判错步骤数 > 0 的真正薄弱项）与平均得分率；
2. **历史时间线**：`history.json` 为 3 名代表性学生（S001 进步型 / S006 顽固错因型 / S009 基础薄弱型）各预置 3 条历史记录。**历史为模拟数据**：数据文件内 `_note` 声明、接口输出逐条 `simulated: true`、前端界面以"模拟历史"徽章显式标注，与本次真实批改结果（"本次批改"徽章）严格区分——不把演示数据伪装成实测数据；
3. **趋势判断规则**（确定性规则，非 LLM）：得分走势以 ±5 个百分点为阈值判"进步 / 下滑 / 持平"；某错因从最近历史记录向前**连续**出现且本次仍出现、累计（含本次）≥ 3 次即判为"顽固错因，建议专项补救"；无顽固错因时比较错因集合变化给出"错因结构好转 / 新增错因"结论。

**班级学情聚合**（`analytics.aggregate`，端点 `/api/analytics/class`）：红黄绿分流占比、平均得分率、知识点错误率（判错步骤数 / 评估步骤总数）、错因标签分布、规则生成的讲评建议（薄弱点 + 主要错因 + 讲评顺序 + 红黄绿分层辅导）。

**讲评课件大纲**（`analytics.build_lecture_outline`，端点 `/api/lecture-outline`）：基于批改证据链自动生成 Markdown 结构化大纲——共性错因前 3（每个挂 1–2 条**匿名**典型错例：学生A/B + 作答原文证据片段 + 判定理由）、薄弱知识点巩固、红黄绿分层任务、5 分钟复测建议（内置 8 个知识点的同型题模板）。可复制导入希沃白板课件或飞书文档（§9.4）。

**知识点—错因—补救资源关联图谱**【设计完成·入围后实施】：以 `(知识点, 错因) --remedied_by--> 资源`、`知识点 --requires--> 前置知识点`、`资源 --retest_by--> 复测题` 的三元组图谱驱动补救练习与复测题推荐（设计方案 §6.21），Demo 中的复测题模板（`RETEST_TEMPLATES`）为该图谱资源节点的最小实装。

## 4. 评语生成策略

评语是系统"温度"的体现，也是命题"个性化评语生成，而非千篇一律"的直接考核点。本章对应设计方案 §9.5、§15.2，代码实现为 `grader.py` 的评语模块。

### 4.1 输入要素与生成约束

个性化评语由四类要素驱动：逐题批改结果（各步得分与失分步骤）、错因标签（本次最关键错因）、历史学习画像（既往高频错因）、进步趋势（错因迁移）。生成约束严格遵循设计方案 §15.2：先肯定已掌握部分 → 只聚焦一个最关键问题 → 给可执行建议 → 不超过 80 字 → 禁用"继续努力 / 再接再厉"等空泛套话 → 语气温和不贬损。

### 4.2 mock 规则模板引擎【Demo 已实现】

mock 模式的评语由**确定性规则模板**拼装（`grader._build_feedback`），核心是"多变体 + 确定性选取"的去模板化机制：

1. **评语结构四段**：
   - **先肯定**：从 5 个开头句式池（`OPENERS`）中选 1 个，填入本次做对的步骤名（如"你在写出正确公式、正确代入数值方面是正确的…"）；全部做错时使用鼓励性兜底句；
   - **指关键问题**：取**扣分最多**的错误步骤，点出步骤名与所属错因（"本次主要问题出在「单位正确」，属于单位错误"）；
   - **给建议**：每个错因标签备有 **3 条措辞变体**的可执行建议（`ADVICE`，共 10 错因 × 3 变体 = 30 条），最多取前 2 个错因各 1 条；
   - **全对正向**：无错因时以具体正向反馈收尾。
2. **确定性变体选取**：以 `md5(seed | salt)` 对变体数取模选取下标——`seed` 为 `submission_id`（临时批改用作答文本本身），`salt` 区分同一条评语内的多个选取点（开头句式、各错因建议），避免彼此联动。**不引入随机数**，效果是：
   - **同错因、不同学生 → 不同措辞**（seed 不同，落到不同变体）；
   - **同一份作答、重复批改 → 逐字一致**（seed 相同，完全可复现，便于评委核验）。
3. **评语查重能力**：`grader.feedback_similarity(texts)` 计算任意两条评语间的最大 difflib 相似度（0–1），用于度量"同一批作业全班评语的措辞分散度"，是设计方案 §15.2"同班去重检查"的可运行度量原语；相似度超阈值触发重写的闭环为生产路径【设计完成·入围后实施】。

### 4.3 LLM 个性化评语【Demo 已实现（llm 模式）】

llm 模式下评语由批改主 Prompt（Prompt 1）的 `student_feedback` 字段一次性产出（受 Prompt 中评语约束节制）；LLM 未返回或返回空时自动回退 §4.2 规则模板，保证任何情况下都有评语。融合历史画像与进步趋势、带同班去重输入的完整评语生成 Prompt 3（输出 `comment / highlight / key_suggestion / char_count`，命中套话词表重写）已入 Prompt 库，为生产路径【设计完成·入围后实施】。

### 4.4 内容安全与教师终审【Demo 已实现终审，安全过滤为设计】

1. **教师可改可否决**【Demo 已实现】：所有评语进入教师工作台为草稿态，教师终审弹窗可修订评语（留空沿用 AI 评语），终审记录落库（本文 §7.4）——AI 评语不绕过教师直达学生；
2. **敏感词与套话过滤、语气校验**【设计完成·入围后实施】：生成后经内容安全过滤拦截敏感、贬损、空泛词，命中重写（设计方案 §19.5）。

### 4.5 对比示例（模板化 vs 本系统）

**示例一（物理 · 速度与单位换算，SUB005：公式计算全对、仅单位错误）**

- 模板化：`本次作业完成较好，继续努力，争取下次取得更好成绩！`
- 本系统：`你在写出正确公式、正确代入数值、计算结果正确方面是正确的，说明基本思路没有问题。本次主要问题出在「单位正确」，属于单位错误。代入数值前先统一单位，最终结果记得写对单位。`

**示例二（数学 · 一元二次方程，SUB002：漏根）**

- 模板化：`还需加强练习，再接再厉。`
- 本系统：`这次作答中选择合适解法、因式分解正确完成得不错，看得出你思考得很认真。本次主要问题出在「求出两个根」，属于步骤缺失。把每一步推理都写在卷面上，检查时逐步核对是否有遗漏。写完后对照题目所求检查一遍，别漏写任何一问的答案。`

两条评语均为 mock 规则引擎的**实际输出**（可复现核验）：开头句式落到不同变体（SUB005 为句式池第 1 式、SUB002 为第 4 式），同为失分评语但措辞完全不同。

对比可见：评语定位到具体步骤、给出可执行动作，且不同学生（不同 seed）落到不同句式变体，从机制上杜绝千篇一律。

## 5. 过程级批改与证据链

本章是系统技术核心之一，对应设计方案 §6.2、§9.4、§9.5、§15.1，代码实现为 `grader.py`。

### 5.1 批改双模式与统一入口【Demo 已实现】

| 模式 | 触发条件 | 行为 |
| ---- | -------- | ---- |
| **mock（默认）** | 未配置任何 LLM 凭据 | 规则引擎按每份作答的逐步预标注（§3.4）沿 Rubric 判分，毫秒级、全确定性，无需网络 |
| **llm** | 配置 `ZHIPI_LLM_API_KEY`（或复用 `ZHIPI_VLM_API_KEY`，多模态模型同样支持纯文本对话，只配一把 Key 也能跑通全链路） | 按 Prompt 1 完整版让 OpenAI 兼容大模型逐步批改并返回 JSON；缺省 `deepseek-chat`（`ZHIPI_LLM_BASE_URL` 默认 `https://api.deepseek.com`） |

统一入口 `grade()`：先取转写 → 有凭据先走 llm，**任何异常自动降级 mock** 并在结果 `note` 中注明降级原因（本文 §7.3）。调用细节：system 提示"你是一名严谨的初中学科教师，只输出 JSON"、`temperature=0`、`response_format={"type":"json_object"}` 强制 JSON 输出（DeepSeek / Qwen 均支持）、超时 30 秒、返回内容容错解析。

### 5.2 批改主 Prompt（Prompt 1 完整版）【Demo 已实现】

工程内模板（`grader.PROMPT_TEMPLATE`）与 Prompt 库 Prompt 1 同源，输入装配：学科 / 学段 / 题型、题干、标准答案、**标准解题步骤**（§3.3）、Rubric（逐步及满分）、学生作答（OCR 转写）、可选错因标签枚举。九条约束原文：

```text
【批改要求】
1. 必须按照评分规则（Rubric）逐项评分，不允许只根据最终答案判断；
2. step_analysis 逐项对应 Rubric，且每步 step 名称必须与 Rubric 步骤同名；
3. 必须指出具体错误步骤及错误位置；
4. 错因标签必须从【可选错因标签】中选择，不得自造标签；
5. 每一步都必须给出 evidence：引用学生作答中的原文片段作为判断依据；
   学生未写出对应内容时 evidence 置为空字符串 ""。

【防幻觉与降级约束】
6. 只能依据学生实际写出的内容评判，不得臆造、补全学生未写出的步骤或结论；
7. 若某步内容无法辨认或存在歧义，将该步 legible 置为 false，如实说明
   「无法辨认 / 存在歧义」，不要猜测其含义，并降低整体 confidence；
8. 若证据不足以判定对错，宁可降低 confidence 交人工，也不得强行给出结论；
9. 只输出 JSON，不要输出多余文字。
```

要求输出的 JSON 结构：`score / max_score / step_analysis[]（step、is_correct、score、error_tag、reason、evidence、legible）/ knowledge_points / error_tags / student_feedback / teacher_note / confidence(0–1)`。其中 **evidence（每步引用学生原文片段）与 legible（可辨认标记）构成证据链的两根支柱**：前者让每个判分可回溯到学生写了什么，后者让"看不清"显性化为教师复核信号，而不是被模型脑补掩盖。

### 5.3 步骤对齐与输出校验【Demo 已实现】

LLM 输出不可全信，`grader.py` 对返回 JSON 做三层工程校验后才进入结果：

1. **步骤名称三级对齐**（`_align_llm_steps`，容忍模型打乱顺序或改写步骤名）：
   - ① 步骤名与 Rubric **精确匹配**；
   - ② 未命中的做 difflib **模糊匹配**（相似度 ≥ 0.6，取最高且每个返回步骤最多使用一次）；
   - ③ 仍未命中**按位置回退**；三级都失败给空步骤（判 0 分），绝不整体错位；
2. **数值边界 clamp**：每步得分强制 clamp 到 `[0, 该步满分]`（四舍五入取整），总分由校验后的逐步得分重新求和，不采信模型自报总分；
3. **枚举与证据链校验**：错因标签不在十类枚举内即丢弃（§3.2）；`evidence` 缺省容错为空串、`legible` 缺省 `true`；`legible=false` 的步骤在判定理由前加 `〔字迹难辨〕` 前缀，前端同步显示"建议教师人工复核"警示条；顶层 `error_tags` 仅合并枚举内标签并去重。

### 5.4 mock 规则引擎判分【Demo 已实现】

mock 分支按 Rubric 逐步取该步预标注：`is_correct=true` 给满分；否则有 `partial_ratio` 按比例四舍五入给部分分；否则 0 分。每步输出与 llm 分支**完全同构**（含 evidence / legible 证据链字段），错因标签同样过枚举过滤——前端与学情模块对两种模式零感知差异。11 份预置作答覆盖全对、部分正确、典型错误、过程不规范、卷面模糊等形态，mock 模式启动自检预批改 11 份的分流结果为绿 5 / 黄 4 / 红 2（由预置因子按 §6 公式确定性算出）。

## 6. 置信度评估与红黄绿分流

本章对应设计方案 §6.5–§6.9、§9.7，代码实现为 `confidence.py`（公式与阈值）+ `grader.py`（因子获取）+ `app.py`（教师通过率回灌）。

### 6.1 五因子公式与阈值【Demo 已实现】

置信度采用百分制（0–100），各因子取值同为 0–100，加权公式与设计方案 §9.7 严格一致（`confidence.py` 中 `WEIGHTS`）：

```text
总置信度 = OCR 清晰度        × 0.25
        + 答案匹配度        × 0.25
        + Rubric 覆盖度     × 0.20
        + 二次批改一致性    × 0.20
        + 历史教师通过率    × 0.10
```

分流阈值（`GREEN_THRESHOLD=85`，`YELLOW_THRESHOLD=60`）：**≥ 85 绿色（自动通过，教师可抽查）；60 ≤ 置信度 < 85 黄色（教师一键确认）；< 60 红色（AI 不直接判分，交人工批改）**。双模型交叉验证是**不占权重的后置防线**：分差 > 满分 15% 一票否决强制转红（本文 §7.2）。

**重归一化**：取值为 `null` 或整个键缺席的因子表示「这一维本次测不出」，其权重从分母剔除，其余因子重新归一——不当 0 分计入。`answer_match` 是这条规则的常态使用者：无题库批改时它必然缺席，若按 0 分算会凭空扣掉 25 分且毫无报错迹象。

**答案匹配度的两条路**：有题库（教师先传答案页）时逐题比对标准答案、按各题分值加权成页级匹配度；无题库时置 `null` 由重归一化剔除。判据是本次批改有没有绑定题库，不靠「有没有 standard_answer 字段」猜。

### 6.2 五因子实现状态表【Demo 已实现，逐因子标注数据来源】

为便于评委核对，下表逐因子列出生产口径、Demo 当前实现与 mock 模式取值来源——**mock 模式下各因子为数据预置的演示值，我们主动亮明，不冒充实测**：

| 因子 | 权重 | 来源与当前实现 | mock 模式取值 |
| ---- | ---- | -------------- | ------------- |
| `ocr_clarity` OCR 清晰度 | 0.25 | **识别引擎输出**：vlm 模式为多模态模型自评 clarity（0–100，clamp 后直接入公式）；生产化后综合 OCR 字符级置信度与版面切分置信度 | 数据预置（与样例图卷面质量分档一致，§2.4） |
| `answer_match` 答案匹配度 | 0.25 | **逐题比对教师答案页**：教师先上传答案页，系统抽出每题标准答案建成本次作业题库；批改时逐题比对学生作答与标准答案，按各题分值加权成页级匹配度。**无题库时置 `null`**，由重归一化剔除——没有基准就没有「匹配度」可言 | 数据预置 |
| `rubric_coverage` Rubric 覆盖度 | 0.20 | **有判定依据步骤占比**（冷启动已实装，`grader.derive_factors`）：批改输出中 `reason` 或 `evidence` 任一非空的步骤数 / 总步骤数 × 100。全对时模型常省略 reason、只留 evidence——旧口径只认 reason 会把满分卷误打成 0；现口径与「评分点是否被真正判到」一致，二者皆空才算未覆盖。解析阶段若有 evidence 无 reason，会回填最小判定说明，避免 UI 空白 | 数据预置 |
| `llm_self_consistency` 二次批改一致性 | 0.20 | **同模型二次批改**（`ZHIPI_DOUBLE_CHECK` 缺省启用）：同 Prompt、temperature=0.3 独立复批一次，程序化比对两次总分与错因标签，`consistency = max(0, 100 − 两次分差绝对值 ÷ 满分 × 200 − 错因标签对称差个数 × 10)`；显式设 `ZHIPI_DOUBLE_CHECK=0` 或二次调用异常时，回退模型自报 confidence（≤1 时 ×100 折算） | 数据预置 |
| `teacher_pass_rate` 历史教师通过率 | 0.10 | **教师审核回灌**（已实装，`app.question_pass_rate`）：按题聚合已审核记录中"确认（未改分）"占比，与冷启动先验 80 分做贝叶斯式平滑——`rate = (80 × 4 + 确认数 × 100) / (4 + 已审核数)`（先验权重 4 次），避免样本极少时置信度大起大落；该题无任何审核记录时沿用预置 / 冷启动默认 80 | 数据预置（教师终审后被真实通过率覆盖，见 §6.4） |

> **通过判定口径**：教师终审中**仅修订评语 / 错因而未改分**（终判分与 AI 分一致）的，视同认可 AI 判分，计入"确认（未改分）"通过——该比率度量的是"AI 判分是否被推翻"，不因教师润色评语或补充错因而记为否定（终审记录已落库 `ai_score` 与 `final_score` 两字段，"未改分"按两者是否一致判定）。

### 6.3 权重设计依据

权重分配基于对批改失败模式的方法论判断（非拟合结果）：

1. **识别 / 转写不确定性是 LLM 批改的主要失败源**——转写错一个符号或单位，后续判分全链路失真，且这类错误 LLM 自身无法察觉。因此与识别质量直接相关的 `ocr_clarity`，与以转写文本为输入、能间接暴露转写失真的 `answer_match`，各占 0.25，**合计 0.50 为最高权重**；
2. `rubric_coverage` 与 `llm_self_consistency` 分别度量批改过程的**可解释完整性**（每步是否给得出判定理由）与**结论稳定性**（两次独立批改是否吻合），是批改环节自身质量的两个正交信号，各占 0.20；
3. `teacher_pass_rate` 是随使用积累的慢变先验，冷启动阶段样本少、方差大，给最低权重 0.10 并配合先验平滑（§6.2），防止早期个别审核动作剧烈拉动分流。

**双模型交叉验证为什么不在这张表里**：它只在黄 / 红件上触发，取值在大多数作答上并不存在。把「大多数时候没有」的东西折进加权，要么得给绿件编一个值，要么让绿件与黄件走两套口径，两条路都不干净。更关键的是语义不同：加权表达「有多少把握」，而两模型结论打架表达的是「这份不能自动放行」——后者应当压过前者，做成一票否决（§7.2）而不是一个可以被其他高分因子稀释的加权项。

**`answer_match` 的适用条件与历史**：该因子度量的是**「学生作答与标准答案的可比对程度」**，服务于置信度（本次批改结果可信、无需人工复核的程度），**不是判分本身**——判分始终由 Rubric 逐项比对完成（§5）。

早期实现取「学生最后一行 vs 一句简短标准答案」，前提是预置题库里恰好有这道题。这个前提在真实作业上几乎不成立，且实测暴露出记号归一问题（docs/08 §九：完全正确的作答因 `x1` 被读成数字 1 而从 100 掉到 25.8），该因子一度被整体移除。

现版本把前提换成**教师上传答案页**：教师用书、批注过的参考卷本就是教师手边的东西，由它建库后逐题比对，这一维才在真实作业上可用，且比对粒度从「整页最后一行」细化到「每一道题」。仍需注意其与判分正确性的耦合（学生真答错时该因子会同步走低），该耦合是否显著已预注册于评测方案 §6 规则 R11。

该权重组合为**设计初值**，其合理性最终以分桶校准实测检验（§6.5）；若实测显示某因子与教师终审一致性弱相关，将按评测方案 §6 的预注册规则调整并保留修订记录。

### 6.4 教师通过率回灌：数据飞轮【Demo 已实现】

教师终审不仅是质量闸门，也实时反哺置信度：教师提交终审后，同题**其余未终审作答的批改缓存立即失效**，下次读取时按最新教师通过率重算置信度——前端可现场演示"教师确认一份 → 同题其他作答的 teacher_pass_rate 因子与置信度实时变化"的完整飞轮（设计方案 §9.7 第 2 道防线）。教师修正数据的更长链路（错例库沉淀 → Prompt 迭代 → 微调语料）为生产路径【设计完成·入围后实施】。

### 6.5 阈值敏感性与验证计划（待实测）

85 / 60 为设计方案 §9.7 给定的**设计阈值**（工程经验设定，未经真实数据校准），其检验已预注册于评测方案：docs/07 §3.4 / 表 D 对绿桶实测"教师认可率"（目标 ≥ 95%，即绿区错放率 ≤ 5%）、对红桶实测"确需人工比例"，并按 §3.5 计算三档 Cohen's kappa；若绿桶认可率不达标，按 docs/07 §6 的预注册规则上调绿色阈值（如 85 → 90）重跑分桶，**调整过程保留修订记录，不事后挑选口径**。在实测完成前，本文不声称 85/60 为最优阈值。

## 7. 可靠性工程

教育场景对"演示不中断、误判不扩散"要求极高。本章汇总 Demo 已实装的可靠性机制，对应设计方案 §6.7、§11.4、§19.1–§19.2。

### 7.1 二次批改一致性（自检）【Demo 已实现】

llm 模式缺省对每份作答**独立复批一次**（`grader.consistency_check`，Prompt 6 思路的工程化实现）：相同 Prompt、temperature=0.3（引入合理扰动），程序化比对两次总分与错因标签集合，按 §6.2 公式折算百分制一致性分，**替代模型单次自报 confidence** 作为 `llm_self_consistency` 因子——两次独立结论的吻合度比单次自我评估更可信。结果随批改输出（`consistency_check: {second_score, agreement}`）在前端展示。环境变量 `ZHIPI_DOUBLE_CHECK=0` 可关闭（省一半批改调用量，成本口径见 §10）；二次调用任何异常静默跳过、回退自报值，不阻断主链路。

### 7.2 双模型交叉验证【Demo 已实现】

配置第二模型三件套环境变量（`ZHIPI_LLM_API_KEY_2` / `ZHIPI_LLM_BASE_URL_2` / `ZHIPI_LLM_MODEL_2`，**三者须配齐**，否则视为未启用）后，**黄 / 红件**自动触发第二模型独立批改（绿区不复核，省调用）。

它是**不占置信度权重的后置防线**，只有一条语义：分差超过**满分的 15%** 视为分歧显著（`escalated`），**无论置信度多少都强制转红交人工**。回传 `cross_check: {model2, model2_score, gap, escalated}` 供教师追溯，界面在转红时说明「两模型分歧显著」。

不把它折成加权因子，是因为加权可被稀释：两模型结论明显打架、而其余各项都高时，总分仍可能停在绿区——恰恰是最该拦下的那种。「有多少把握」（加权）与「这份不能自动放行」（否决）是两种不同的判断，后者必须能压过前者。

第二模型异常静默跳过，等同于未触发，不影响置信度。它与二次批改一致性构成两个正交信号：后者查同一模型的稳定性（随机性误差），前者查跨模型的系统性偏差——同模型批两次会一样地错，只有换模型才测得到。

**选型与超时预算（实测结论）**：本路径的失败是静默的——拿不到结论即跳过，界面无任何提示。因此"配了第二模型"与"交叉验证真的在跑"是两件事，必须实测确认。第二模型的独立超时由 `ZHIPI_CROSS_TIMEOUT` 控制（缺省 12 秒），**该缺省值对实测过的所有候选都不够**：中转网关上同一道题重复批改，`grok-4.5` 77–91 秒、`glm-5.2` 45–65 秒、`glm-4.5-flash` 49–72 秒、`minimax-m3` 25–90 秒（中位 62 秒）——名字带 flash / fast 的并不更快。预算配小的后果不是"少一份佐证"，而是**黄 / 红件白等满预算秒数再拿到 `None`**，比不启用更差。

选型还须看判分稳定性，而非只看速度：实测 `glm-4.5-flash` 会给满分卷扣到 9 分、同一份错卷判分在 2–4 分间漂动（跨越满分 15% 的转红阈值），这类裁判会把好卷误判成"两模型分歧"强制转人工，反而用噪声灌满人工队列；`qwen3.5-2b` 更极端（给全对作答 2/10）。现选 `minimax-m3`（错卷三次均 4 分、满分卷两次均 10 分，与主模型分差稳定 ≤ 1.0 分），配 `ZHIPI_CROSS_TIMEOUT=120`。实测脚本：`demo/tools/bench_second_model.py`。

**成本与等待的真实口径**：绿区不触发交叉验证，故只有黄 / 红件承担这份延迟——单份总等待 ≈ 主批改 3.4 秒 + 二次复批 3.4 秒 + 交叉验证约 62 秒 ≈ **70 秒**。这部分作答本就要转人工复核，多花一分钟换一份跨模型佐证是合理交换；但现场演示若不愿等，应把 `ZHIPI_LLM_MODEL_2` 留空**明确停用**，而不是留一个必然超时的配置。

### 7.3 全链路降级策略表【Demo 已实现】

任何外部依赖失败都有明确降级路径，保证"现场演示永不空转"（设计方案 §11.4）：

| 故障点 | 触发条件 | 降级行为 | 用户可见性 |
| ------ | -------- | -------- | ---------- |
| LLM 批改调用 / 解析失败 | 网络、超时、返回非法 JSON | 自动降级 mock 规则引擎 | 结果 `mode="mock"` + `note` 注明降级原因 |
| VLM 识别失败、图片命中内置样例 | 多模态接口异常 | 降级 sample-match，返回样例标准转写 | `engine="sample-match"` |
| VLM 识别失败、未命中样例 | 同上 | 返回 `engine="none"` + 错误说明，不批改 | 前端"识别失败"提示 |
| 未配置 VLM、未命中样例 | 离线模式上传陌生图片 | `engine="none"` + 引导配置 Key 的提示 | 前端引导文案 |
| 二次批改一致性异常 / 关闭 | `ZHIPI_DOUBLE_CHECK=0` 或调用异常 | 静默跳过，`llm_self_consistency` 回退模型自报值 | 因子面板无二次批改条目 |
| 第二模型异常 / 未配齐 | 交叉验证调用失败 | 静默跳过交叉验证 | 无交叉验证条目 |
| 临时批改（任意上传）失败 | LLM 异常且无预置标注可回退 | HTTP 502 + 失败原因 | 前端"批改失败"提示 |
| 飞书卡片推送失败 | Webhook 网络 / 接口异常 | 降级 `mode="demo"`，返回将推送的卡片内容 + 失败原因 | 页面黄条"演示模式" |
| 飞书写表失败 | 鉴权 / 频控 / 字段不匹配等任何异常 | 降级 `mode="demo"`，返回将写入的记录 + 失败原因 | 页面黄条"演示模式" |

另有**启动自检**：mock 模式启动时预批改全部 11 份作答并打印红黄绿分布（绿 5 / 黄 4 / 红 2），既预热缓存又在开场前验证全链路健康；llm 模式跳过预批改（现场按需真实批改），教师工作台首次加载时以 4 线程并发批改并轮询 `/api/grade-progress` 展示"已批改 x / y"。

### 7.4 教师终审校验与状态管理【Demo 已实现】

`POST /api/teacher/review` 是教师最终裁决权的落点，服务端做三重校验（非法输入整单拒绝）：

1. **动作枚举**：`teacher_action` 为 `Literal["confirmed", "modified"]`，非法值由 FastAPI 校验直接 422；
2. **分数边界**：`final_score` 必须在 `[0, 该题满分]` 内，越界返回 422 并说明合法区间；
3. **错因枚举**：`final_error_tags` 逐个校验 §6.11 十类枚举成员资格，含非法标签返回 422 并列出非法项；`final_error_tags=None` 语义为"沿用 AI 错因"，与"改判为空（清空错因）"严格区分。

终审记录（AI 分 / 终分 / 错因修订 / 评语修订 / 动作）写入内存态 `REVIEWS`，同题未终审作答缓存失效触发置信度重算（§6.4）。其他工程细节：上传图片限 8MB、base64 解码失败 400；样例图片文件按 manifest 白名单校验文件名，防路径穿越；批改结果按 `submission_id` 缓存，重复请求不重复计费。

## 9. 飞书 AI 产品能力集成实现

本章对应设计方案 §13.2《飞书 AI 产品能力集成设计》，落地"批改在系统、协同在飞书"原则。代码实现为 `demo/pipeline/feishu.py`（接口 `/api/feishu/push`、`/api/feishu/sync-base`）。

### 9.1 双轨运行口径【Demo 已实现】

集成点一、二为**双轨可运行代码**：**未配置凭据时为演示模式（`mode="demo"`）**，返回"将推送的卡片内容"与"将写入的表格记录"供页面预览；**配置凭据后为 live 模式（`mode="live"`）**，互动卡片经自定义机器人 Webhook 真实推送、《学情台账》经开放平台鉴权后 `batch_create` 真实写入多维表格。**现场演示采用 live 模式**（真实飞书环境实推实写），演示模式仅作为断网 / 凭据故障时的兜底；live 链路任何异常（网络、鉴权、频控、写表报错）自动降级演示模式并注明原因，保证演示不中断（§7.3）。集成点三、四为入围后随企业教练搭建【集成点三：设计完成·入围后实施；集成点四：部分实现】。

### 9.2 集成点一：多维表格 AI 学情台账（主用飞书 AI 能力）【Demo 已实现】

批改完成后，系统将逐题结果（叠加教师终审）组装为多维表格记录批量写入班级《学情台账》。前 8 个字段由系统写入（`build_base_records`），后 2 个由飞书 **AI 字段捷径**在表格内逐行生成：

| 字段 | 类型 | 来源 | 说明 |
| ---- | ---- | ---- | ---- |
| 学生 | 文本 | 系统写入 | 学生姓名 |
| 题号 | 文本 | 系统写入 | 题目 ID + 标题（如 `Q002 · 速度与单位换算`） |
| 得分 | 数字 | 系统写入 | 本题教师前 AI 得分 |
| 满分 | 数字 | 系统写入 | 本题满分 |
| 错因标签 | 文本 | 系统写入 | §6.11 枚举标签顿号连接，空则"无" |
| 置信度 | 数字 | 系统写入 | §9.7 五因子加权结果 |
| 分流状态 | 单选/文本 | 系统写入 | `绿色 · 自动通过 / 黄色 · 教师确认 / 红色 · 人工批改` |
| 教师终审 | 文本 | 系统写入 | `已确认 x/y` / `已修改 x/y（含错因修订）` / `待终审` |
| 一句话错因摘要 | **AI 字段捷径** | 飞书 AI 生成 | 提示词见下 |
| 个性化学习建议 | **AI 字段捷径** | 飞书 AI 生成 | 提示词见下 |

**AI 字段捷径两列提示词**（在多维表格内对相应列配置，错因摘要与学习建议由飞书 AI 能力逐行生成，无需系统侧再调大模型）：

- **一句话错因摘要**列：输入引用本行【错因标签】与【分流状态】，提示词要点为"依据本行错因标签与分流状态，用不超过 30 字客观概括该生本题的主要问题，只陈述错在何处、不作评价；错因标签为'无'时输出'本题无错因，作答正确'"；
- **个性化学习建议**列：输入引用本行【错因标签】与【得分】/【满分】，提示词要点为"依据本行错因标签与得分情况，给出一条具体、可执行的补救建议（先补哪个知识点、做几道何种练习），不超过 40 字，语气温和，禁用'继续努力'等空泛套话（§15.2 约束）"。

**仪表盘用法**：基于该表建多维表格仪表盘——按「分流状态」出红黄绿占比饼图、按「错因标签」出错因分布柱状图、按「题号」透视错误率，等价于把班级薄弱点分析搬进飞书；学情以结构化资产沉淀在学校自有飞书空间，教研组无需登录系统即可协作。

### 9.3 集成点二：机器人互动卡片审核流转【Demo 已实现】

**接入方式**：教师群添加飞书自定义机器人，Webhook 地址注入 `ZHIPI_FEISHU_WEBHOOK`，系统以 `msg_type=interactive` POST 卡片消息（无需应用鉴权，接入成本最低）。

**卡片结构**（`build_review_card`，与代码逐要素对应）：`header`（标题「📋 作业批改完成 · 待审核提醒」，蓝色模板，宽屏模式）→ 概览区（作业名、参与作答人数、平均得分率，lark_md 富文本）→ 分隔线 → 红黄绿分流统计（🟢🟡🔴 信号灯逐行列数）→ 醒目的「⏳ 待教师处理」数量（黄 + 红）→ 主要错因（错因分布前三）→ 分隔线 → `action` 按钮「前往审核工作台」（跳转链接经 `ZHIPI_REVIEW_CONSOLE_URL` 注入，缺省占位）→ 落款 `note`。

**审核流转闭环**：卡片提醒 → 教师点按钮跳转红黄绿审核工作台 → 确认 / 改分 / 改判错因 / 修订评语 → 终审结果回写并可再同步台账（台账「教师终审」列随之更新）；教师终审后向家长推送个性化评语卡片为设计方案 §13.2 集成点二第 2 条【设计完成·入围后实施】。全程教师持最终裁决权（设计方案 §6.9）。

### 9.4 集成点三 / 四【设计完成·入围后实施 / 部分实现】

**集成点三（知识问答 / Aily 讲评助手）**：将两层标签体系、各题 Rubric 与标准解题步骤、历次学情报告沉淀入飞书知识库；教师在飞书内向"讲评助手"提问（如"本次速度题主要错因是什么？下节课怎么讲？"），基于知识库给有据回答；入围后配合企业教练用 **Aily** 搭建为正式智能体应用、用 **妙搭** 低代码搭建读写台账的教师端轻应用。

**集成点四（飞书文档 AI 讲评提纲）**【部分实现】：讲评课件大纲一键生成（Markdown，`/api/lecture-outline`）已在 Demo 实现，可直接粘贴入飞书文档（自动识别标题层级）；导出后用文档 AI 润色排版、供教研组协作批注为入围后实施。

### 9.5 开放平台鉴权与写表要点【Demo 已实现】

集成点一的真实写表链路（`sync_to_base`）：

1. **鉴权**：以 `app_id` + `app_secret` POST `/open-apis/auth/v3/tenant_access_token/internal` 换取 `tenant_access_token`（有效期约 2 小时，超时 10 秒；响应 `code != 0` 判为鉴权失败）。生产环境应缓存复用、临期刷新；
2. **批量写入**：以 `Authorization: Bearer {token}` POST `/open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records/batch_create`，请求体 `{"records": [{"fields": {...}}]}`（超时 15 秒；响应 `code != 0` 判为写表失败）；单次上限 500 条，`fields` 键名须与表列名完全一致；
3. **频控与重试**：命中开放平台频控（HTTP 429 / 频控错误码）按指数退避重试、超 500 条分片提交为生产化要点【设计完成·入围后实施】；Demo 中任何写表异常统一降级演示模式（§7.3），保证现场不中断。

## 10. 成本估算卡

> **估算口径声明**：本节全部为**刊例价数量级估算**，用于说明成本结构与可负担性；单价以各厂商官网最新刊例为准（大模型 API 价格调整频繁），实际 token 消耗以评测方案（docs/07）跑通后的实测记录为准。**本节不含任何实测数字。**

### 10.1 计费单价（公开刊例数量级，以官网最新为准）

| 用途 | 模型（Demo 缺省） | 刊例数量级（估算） |
| ---- | ----------------- | ------------------ |
| 多模态识别 | qwen-vl-max（阿里云百炼） | 输入约 ¥0.003 ~ 0.02 / 千 token 档（历次调价区间），输出略高 |
| 文本批改 | deepseek-chat（DeepSeek 开放平台） | 输入约 ¥0.001 ~ 0.002 / 千 token 档（缓存命中更低），输出约 ¥0.002 ~ 0.008 / 千 token 档（历次调价区间，现行刊例见《03-行业研究》§6.1） |

### 10.2 单份作业成本算式框架

按 Demo 实际链路"**识别 1 次 + 批改 2 次**（主批 + 二次一致性复批，`ZHIPI_DOUBLE_CHECK` 缺省开启）"估算 token 数量级：

```text
识别 1 次：作业照片图像 token 约 1k–2.5k + 转写 Prompt 与输出约 0.3k
           ≈ 1.5k – 3k token
批改 2 次：每次输入（题干 + Rubric + 标准解题步骤 + 作答 + 约束）约 1k–1.5k，
           输出（逐步 JSON）约 0.5k–1k
           ≈ 3k – 5k token
──────────────────────────────────────────────
单份合计 ≈ 5k – 8k token（数量级）

单份成本 ≈ 识别 token × 多模态单价 + 批改 token × LLM 单价
        ≈ ¥0.01 – 0.07 / 份（数量级：几分钱，上限约一角）
```

与《03-行业研究与竞品分析》§6.1 口径互引：该节「单份约 2 分钱」为**单份 token 消耗上界 × 现行刊例价**的口径，本节按历次调价带取价的上限约 ¥0.07/份，两个口径的量级结论一致（几分钱、上限约一角），不变。

黄 / 红作答另触发双模型交叉验证 +1 次批改（§7.2）；按红黄占比三到五成估计，整体成本上浮约 15% ~ 25%，仍在同一数量级。

### 10.3 班级 / 学期成本外推（估算）

```text
40 人班级 × 1 次作业        ≈ ¥0.4 – 2.8 / 次
40 人 × 每周 5 次 × 20 周学期 = 4000 份
                            ≈ ¥40 – 280 / 班 / 学期（数量级：几十到二三百元）
```

即使按估算区间上限，单班学期成本也远低于一名教师每天 2–3 小时批改时间的机会成本，验证方案经济可行。**降本杠杆**（均已在工程中留有开关或路径）：绿色高置信度作答不重复批改（缓存复用）；`ZHIPI_DOUBLE_CHECK=0` 可省一半批改调用；交叉验证仅黄 / 红触发；生产化后简单客观题走规则 / 轻量 OCR 不调大模型；国产模型私有化部署后边际成本转为 GPU 摊销（设计方案 §13.1）。

> 再次强调：以上为估算口径，实测的单份 token 消耗与成本记录，以 docs/07 评测跑通后填入的运行环境与结果表为准。
