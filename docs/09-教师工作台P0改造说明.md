## 1. 背景与问题

### 1.1 现有能力（Demo 已实现）

教师工作台（Tab 03）当前已打通：

1. 全部作答红黄绿审核列表；
2. 绿色抽查通过 / 黄红一键确认；
3. 终审弹窗：改总分、改判错因（§6.11 十类枚举）、修订评语；
4. 终审回灌该题「历史教师通过率」因子，同题未终审作答置信度实时重算。

对应实现：

| 层 | 位置 |
| -- | ---- |
| 列表与弹窗 | `demo/static/js/app.js` → `loadTeacher` / `openReview` / `submitReview` |
| 列表 API | `GET /api/teacher/results`（`demo/app.py`） |
| 终审 API | `POST /api/teacher/review`（`demo/app.py`） |
| 会话隔离 | `demo/pipeline/session_store.py`（审核记录按浏览器会话存放） |

### 1.2 真实教师视角的缺口

以一线教师批改作业的工作流审视，当前最大落差不在「AI 聪不聪明」，而在「老师能不能像改作业一样改 AI 的判断」：

| # | 缺口 | 表现 | 影响 |
| - | ---- | ---- | ---- |
| 1 | 审卷上下文断裂 | 终审弹窗只有总分/错因/评语，无 OCR、无逐步证据；要看证据须跳回 Tab 02 | 认知切换成本高，难「审」只能「信或改总分」 |
| 2 | 无步骤级改判 | 过程级批改的核心是某一步该不该给分，但终审只能改总分 | 证据链对老师只读，裁决权未落到评分点 |
| 3 | 无筛选与待审队列 | 列表平铺，无按红黄绿/题目/错因/未审过滤，无「最可疑优先」 | 班级规模放大后找不到该先看的卷 |
| 4 | 无批量处理 | 同题同错因须一份一份点确认 | 减负感不足，红黄绿易沦为颜色装饰 |

> **一句话定位本轮改造**：把教师工作台从「总分级确认台」升级为「步骤级审卷台」。

## 2. 改造目标与非目标

### 2.1 目标（P0）

把现有动线：

```text
列表点确认 / 弹窗改总分
```

升级为：

```text
同屏审卷 → 按步骤改判 → 按题/错因筛选 → 同类批量确认
```

原则：

1. **最小改动**：优先复用现有会话审核、通过率回灌、红黄绿公式，不重写批改主链路；
2. **可演示**：改造后 5 分钟内能讲清「老师按评分点终审，而不是只改一个总分」；
3. **兼容旧行为**：不传步骤改判时，仍可只改总分/错因/评语；
4. **不破坏飞轮**：`question_pass_rate` 仍以「终判分是否等于 AI 分」判定确认通过。

### 2.2 非目标（本轮明确不做）

| 项 | 说明 | 阶段 |
| -- | ---- | ---- |
| 老师在线编辑 / 新录入 Rubric | 出题配尺子是刚需，但模型与 UI 面更大 | P1 |
| 学生端订正回流 | 错因画像从统计变干预的关键一环 | P1 |
| 调整 §9.7 五因子权重 | 权重预注册，无新实测不改；2026-08-09 的权重变更属**因子集合变更**（移除 answer_match、新增 cross_model_agreement）连带的重新分配，不是按实测数据拟合，且刻意保证「未触发交叉验证时」的口径与旧四因子完全一致 | 保持 |
| 学情聚合全面切换到教师步骤终审 | 避免一次改 analytics 全链路 | P1（见 §6.5） |
| 多班级账号 / 复杂权限 | Demo 会话隔离已够答辩 | 生产化 |

### 4.2 块 B · 步骤级改判（P0-2，核心）

**教师价值**：能说「第 2 步其实对了，第 3 步才该扣」，而不是只改一个总分。

#### 会话审核记录扩展

现有结构：

```json
{
  "submission_id": "SUB002",
  "teacher_action": "modified",
  "ai_score": 6,
  "final_score": 7,
  "max_score": 10,
  "final_error_tags": ["步骤缺失"],
  "final_comment": "…",
  "reviewed": true
}
```

扩展可选字段 `final_steps`：

```json
{
  "final_steps": [
    {
      "step_id": 1,
      "step": "选择合适解法",
      "ai_score": 2,
      "final_score": 2,
      "max_score": 2,
      "error_tag": null,
      "teacher_override": false
    },
    {
      "step_id": 3,
      "step": "求出两个根",
      "ai_score": 1,
      "final_score": 2,
      "max_score": 3,
      "error_tag": "步骤缺失",
      "teacher_override": true
    }
  ]
}
```

#### 业务规则

1. **默认** `final_score = Σ final_steps[].final_score`（前端自动汇总）；
2. 若允许老师再微调总分，提交前须提示「与步骤分之和不一致」，**服务端以 steps 求和为准**或拒绝不一致请求（二选一，实施时锁定一种）；
3. 某步分数或错因相对 AI 原判有变化 → `teacher_override = true`；
4. 请求不带 `final_steps` → **完全兼容旧行为**（只改总分/错因/评语）；
5. 总览 `final_error_tags` **优先于**步骤级 `error_tag` 聚合（总览有值则覆盖；总览未传则可由步骤聚合）；
6. `question_pass_rate` 口径不变：`final_score == ai_score`（且未改分语义下的 confirmed）仍计为通过。

#### 后端

`ReviewReq` 增加：

```text
final_steps: list[StepReview] | None
```

`StepReview` 最小字段：

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| `step_id` | int | 必须落在该题 Rubric |
| `final_score` | float | `0 ≤ score ≤ 该步 max_score` |
| `error_tag` | str \| null | 若有值须 ∈ §6.11 枚举 |

校验失败返回 `422`，错误信息可读。

写入 `session["reviews"][sid]` 时保留 `final_steps`（无则省略字段，兼容老记录）。

#### 前端

审卷面板每步可编辑：

- 分数输入（0 ~ max，步长 0.5）；
- 错因下拉（可空 = 无错因/沿用）；
- AI 原判分、`reason`、`evidence` **只读**展示；
- 总分展示为自动汇总；提交时若有步骤改动则带上 `final_steps`。

#### 验收

将物理题「单位正确」从 0 改为 1 → 总分自动 +1 → 提交后列表为「已修改」→ 该题通过率按是否改分正确回灌。

### 4.3 块 C · 筛选、排序与人话置信度（P0-3）

> ✅ **已实现**（2026-08-06）：`#teacher-body` 上方已加筛选条（状态：全部/未审/已审/红/黄/绿；题目；错因），默认排序红→黄→绿、同级置信度升序、未审优先。

**教师价值**：先看到该看的卷，而不是平铺 11/40 份。

#### 前端过滤条（可纯前端，不强制改 API）

置于 `#teacher-body` 表上方：

| 筛选项 | 取值 |
| ------ | ---- |
| 状态 | 全部 / 红 / 黄 / 绿 / 未审 / 已审 |
| 题目 | 全部 + 各题目标题（或 `question_id`） |
| 错因 | 全部 + §6.11 枚举（含「无错因」） |
| 排序 | 默认 **红 → 黄 → 绿**；同级按置信度**升序**（最不自信优先） |

#### 人话置信度（低成本高观感）

列表行或审卷头部，将五因子翻成一句决策语言，例如：

> 进入黄桶：字迹清晰度一般（72）+ 有 1 个评分点未给出完整判定理由

避免在老师主路径上堆 `§9.7` / `LLM` 等工程术语；技术明细可折叠。

#### 验收

一键只看「黄色 + 某错因 + 未审」，且排序把最不自信的提前。

### 4.4 块 D · 批量确认（P0-4）

**教师价值**：同题同错因不必点十次。

#### 前端

- 行首 checkbox +「全选当前筛选结果」；
- 批量动作（P0）：
  1. **批量确认**（不改分，`teacher_action=confirmed`）；
  2. **批量抽查通过**（仅绿桶，语义同单条抽查）。
- 明确**不做**批量改分（防误伤）。

#### 后端

新增：

```http
POST /api/teacher/review-batch
```

请求示例：

```json
{
  "submission_ids": ["SUB004", "SUB007"],
  "teacher_action": "confirmed"
}
```

行为：

1. 循环复用单条终审逻辑（同一会话、同一校验）；
2. 单次上限建议 50；
3. 返回：`ok_count` / `fail_list` / 受影响题目的 `question_pass_rate` 映射。

#### 验收

筛选「同题 + 同错因 + 黄桶未审」→ 全选 → 批量确认 → 出现通过率回灌提示。

## 5. 接口级变更草案

### 5.1 `GET /api/teacher/results`（扩展字段）

在现有摘要字段基础上，每行增加 §4.1 所列审卷上下文。  
响应仍包含 `error_tags_enum`，供错因多选与筛选共用。

### 5.2 `POST /api/teacher/review`（扩展 body）

```json
{
  "submission_id": "SUB002",
  "teacher_action": "modified",
  "final_score": 7,
  "final_error_tags": ["步骤缺失"],
  "final_comment": "漏根已指出，过程分给回 1 分",
  "final_steps": [
    {"step_id": 3, "final_score": 1, "error_tag": "步骤缺失"}
  ]
}
```

兼容：省略 `final_steps` 时行为与现网一致。

### 5.3 `POST /api/teacher/review-batch`（新增）

见 §4.4。P0 仅允许 `teacher_action: "confirmed"`（若实现抽查通过，可复用 confirmed + 仅绿桶前端约束）。

### 5.4 会话结构

`session["reviews"][sid]` 增加可选 `final_steps`。  
老记录无该字段时：前端按 AI `step_analysis` 只读展示，不视为步骤级终审。

### 5.5 明确不改的接口/模块（P0）

| 模块 | 原因 |
| ---- | ---- |
| `grader.py` 主批改与 mock 标注 | 终审是后置裁决，不回写 AI 基线 |
| `confidence.py` 权重与阈值 | 预注册口径 |
| `POST /api/grade` / 图片批改链路 | 与教师台解耦 |
| `analytics.py` 聚合主逻辑 | P0 仍读 AI 步骤；见 §6.5 |

## 7. 风险与规避

| 风险 | 规避 |
| ---- | ---- |
| 步骤分之和 ≠ 总分 | 服务端强制以 steps 求和为准，或提交前前端锁定并校验 |
| 步骤错因与总览错因冲突 | 总览 `final_error_tags` 优先 |
| 列表 payload 变大 | Demo 可接受；体量上来再拆详情 API |
| 破坏通过率飞轮 | 保持「未改分视同确认」；只改评语/错因且分不变仍算通过 |
| 老师看不懂因子 | 主路径用人话一句；工程因子折叠 |
| 批量误确认 | P0 禁止批量改分；二次确认文案带上筛选条件与份数 |
| `step_id` 缺失或不稳 | 以题目 Rubric 的 `step_id` 为准对齐；展示名用 `step` 字段 |

## 8. 改造后演示脚本（5 分钟）

1. 打开 **03 教师工作台** → 筛「黄桶 / 未审」；
2. 点开一份物理速度题 → **同屏**查看 OCR 与「单位正确」步骤证据；
3. 仅改第 4 步 0 → 1 → 总分自动更新 → 提交终审；
4. 出示提示：该题教师通过率回灌、同题其他作答置信度变化；
5. 再筛「同类错因」→ 全选 → **批量确认**；
6. 收束：

> AI 负责过程级初判与证据链；老师按评分点终审。  
> **裁决权在步骤，不在一个总分框。**

### 批量上传 / 批量识别批改（已实现 · Demo 前端流水线）

真实课堂动线不是「选一张图 → 看一份结果」，而是：

```text
连拍/选多张 → 批量识别 → 批量批改 → 工作台按红黄绿审 → 只人工碰低置信
```

**现网实现（2026-03-22 已落地）**：

| 能力 | 现网 |
| ---- | ---- |
| 选图 | `#file-input` 已支持 `multiple`，拖拽多文件同样进入批量 |
| 触发 | 一次选 1 张 → 走原单张动线（可修正转写）；**≥2 张 → 自动进入批量流水线** |
| 处理 | 前端串行：每张「压缩 → `/api/recognize-image` → `/api/grade-image`」，进度条 + 逐张状态（待处理 / 识别中 / 批改中 / 成功 / 失败原因） |
| 失败隔离 | 单张识别失败（离线模式未命中样例 / 超限 / 判题失败）不阻断整批，列表标注原因 |
| 上限 | 单次 ≤ 20 张（`BATCH_MAX`，与后端 `upload_max` 对齐），超限提示拆批 |
| 结果去向 | 成功张全部写入会话 `uploads` → 教师工作台「我的上传」；完成卡片提供「去工作台审核」入口 |

**未做（有意保留）**：

1. 批量不加后端新接口——复用现有单张 API 串行调用，避免重复实现 `_rate_guard` / 配额 / 会话写入；
2. 批量模式不做逐张 OCR 人工确认（单张动线保留该能力）；批量完成后按红黄绿去工作台复核；
3. 配额口径不变：识别/批改按张累计，`guard.quota_take` 照常扣减。

**老师目标体验一句话**：

> 我把本子拍完就走开；回来只审红黄桶，绿桶抽查即可。
